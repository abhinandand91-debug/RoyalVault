# Royal Vault

A premium Egyptian art-deco slot game. Act as a senior Unity gameplay engineer: understand before changing, and prefer the smallest complete change over speculative frameworks.

## Project Facts

- Unity 6000.3.10f1, Built-in render pipeline, uGUI with TextMeshPro, the old Input Manager.
- Packages: PrimeTween (npm registry), UIParticle (Git URL), Unity Test Framework.
- Assemblies: `GameKit` and `GameKit.UIParticle` (reusable UI and animation), `SlotKit.Core` (plain C# slot engine), `RoyalVault.Core` (machine presets), `RoyalVault.Unity`, `RoyalVault.Editor`, and the two test assemblies.
- Entry points: `Boot.unity` with `AppEntry` and `LoadingScreen`, then `GameBootstrap` on the `RoyalVaultGame` prefab.
- The prefab, scenes, theme and presets are generated by **Royal Vault > Build Everything**.
- Saving: JSON in PlayerPrefs through `ISaveStore`; story and sound flags in PlayerPrefs keys.
- No networking. Target platforms are not set yet.
- Detailed rules live in `.claude/rules/` (architecture, slot rules, Unity lifecycle and assets, testing, git).

## Workflow

1. **Orient:** check `git status --short` and read the code involved before editing.
2. **Trace:** follow the feature from `GameBootstrap` through SlotKit, the views and the tests; reuse existing patterns.
3. **Plan:** for multi-file or risky work, state the files, approach and checks first.
4. **Implement:** focused changes; keep serialized fields, GUIDs and public APIs stable.
5. **Verify:** compile, run the relevant tests (unless the user said to skip them), review the diff.
6. **Report:** what changed, which files, which checks actually ran and their results, and any risks.

## C# Coding Standards – Mandatory

Follow traditional, clean, and consistent C# coding conventions throughout the entire Unity project.

### 1. Brace Style

- Always use Allman brace style.
- Opening braces `{` must be on a new line.
- Closing braces `}` must be on a separate line.
- Always use curly braces for `if`, `else`, `else if`, `for`, `foreach`, `while`, and other control flow statements.
- Never omit braces, even for single-line statements.

### 2. Statement Formatting

- Write only one statement per line.
- Never combine multiple statements on a single line.
- Keep method calls, assignments, declarations, and return statements on separate lines.
- Avoid overly compressed or condensed code.

### 3. Conditional Statements

Always write:

```csharp
if (condition)
{
    ExecuteAction();
}
else
{
    HandleAlternative();
}
```

Never write:

```csharp
if (condition) ExecuteAction();
```

### 4. Methods and Classes

- Use Allman style for class, method, property, and namespace declarations.
- Keep method bodies properly indented.
- Separate logical code sections with blank lines.
- Keep methods focused and readable.

### 5. General Guidelines

- Use 4 spaces for indentation.
- Avoid unnecessary one-line methods and expressions.
- Prefer readability and maintainability over fewer lines of code.
- Follow consistent naming conventions: PascalCase for classes and methods, camelCase for local variables and private fields.
- Do not reformat unrelated files unless explicitly requested.

### 6. Naming and Types

- PascalCase for namespaces, types, methods, properties, events and enum members; interfaces start with `I`.
- Names say what something is in the game (`spinRequest`, not `data`, `manager` or `temp`); booleans read naturally (`isReady`, `canSpin`).
- `private` by default; expose the smallest API needed; properties instead of public mutable fields.
- `readonly` for references set once, `const` for compile-time constants; no unexplained magic numbers.
- Prefer early returns to deep nesting, and composition to inheritance.
- Add interfaces only at real seams (saving, randomness, clock, replaceable rules), not for every class.
- Use `TryGet...` / `TryParse...` for expected failures; no exceptions for ordinary branching, no empty `catch`.
- No `async void` outside Unity event boundaries.

### 7. Enforcement

These coding standards are mandatory for all newly generated or modified C# files.
Before completing a task, review the modified files and correct any formatting violations.
`.editorconfig` and `CodingStandardsTests` enforce the brace and line rules.

## Performance Standards – Mandatory

The game will keep growing, so every runtime feature is written to scale from the start.

### 1. Animation

- Use PrimeTween for all timed animation: fades, moves, scales, colours, delays and chains.
- Use a PrimeTween `Sequence` instead of a coroutine when the timing is fixed.
- Use a coroutine only when the code waits on the player or on game state (a tap, a reel landing, a scene load).
- Keep the `Tween` or `Sequence` handle in a field and call `Stop()` on it when the animation is cancelled.

### 2. No Allocations in Hot Paths

- Hot paths are `Update`, `LateUpdate`, coroutine loops, tween callbacks and anything that runs every spin.
- Do not create classes, arrays, lists or delegates there; reuse fields instead.
- Do not use LINQ there.
- Do not build strings there; update text only when its value changes.
- Tween callbacks must not capture locals or `this`: use the target overload, for example
  `Tween.Custom(this, 0f, 1f, duration, (view, value) => view.SetGlow(value))`.
- Cache `WaitForSeconds` and other yield instructions in fields.

### 3. Cached References

- Never call `GetComponent`, `Find`, `FindObjectOfType` or `Camera.main` in hot paths.
- Get references once in `Awake`, `Setup` or through serialized fields.

### 4. Object Pooling

- Pool what is spawned often (win effects, coins, popups) instead of `Instantiate` and `Destroy`; one-off objects need no pool.
- A pooled object resets all its state on reuse (tweens, coroutines, colours, subscriptions), and every pool has a size limit.
- Use Unity's `UnityEngine.Pool.ObjectPool<T>`; `SymbolFxLayer` is the reference example.

### 5. UI

- Turn off `raycastTarget` on every graphic that is not clickable.
- Put frequently changing UI (counters, effects) on its own nested `Canvas` so the whole screen does not rebuild.
- Avoid layout groups on animated content; position elements directly.
- Fade groups with `CanvasGroup.alpha` rather than toggling many objects.

### 6. Events and Lifetime

- Unsubscribe from events on longer-lived objects in `OnDestroy`.
- Stop tweens and coroutines that a view owns when it is disabled or destroyed.

### 7. Textures, Audio and Draw Calls

- `TextureBudget` (run by Build Everything) sets every game texture to BC7 on desktop and ASTC on mobile, without mipmaps or readable copies; never leave art uncompressed.
- Texture sizes must be multiples of 4 so they can compress; pad new art with transparent pixels if needed.
- Reel symbols are 504 px and packed by `SpriteAtlases` into one atlas for stills and one for motion blur, so the reels batch.
- Moving or fading parts of the screen live on their own nested `Canvas` (`UiFactory.NestedCanvas`); overlays that fade out use `CanvasAutoHide`.
- Particles in UI use `UiParticleEmitter`, which draws all particles as one mesh.

### 8. Measure

- Run `PerformanceProbeTests` (set `ROYALVAULT_PERF` to an output file) before and after performance work and compare the numbers.

- Profile with the Unity Profiler before micro-optimising; fix what the profiler shows first.
